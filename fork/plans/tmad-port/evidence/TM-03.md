## Brief requirements — how each is met

1. **Canonical submission owner.** `dispatchComposerAgentMessage` is untouched. Queue
   admission (`queueComposerMessage` / `queueComposerMessageOnServer`) only appends to the
   queue writer and never sees a submission writer; the optimistic row is a queued row, not
   a timeline row. Tested: `actions.test.ts > "admits with the explicit queue intent and
   never touches a submission writer"`, `session-store.test.ts > "never creates a submitted
   timeline row"`, and the e2e asserts exactly one canonical `user_message` row carrying
   the delivered (edited) text after drain.
2. **Capability gate.** Every durable path gates on `server_info.features.durableAgentQueueV1`
   (composer selector + session-context flush), tagged
   `COMPAT(durableAgentQueue): added in v0.11.0-beta.3+custom (TM-02/TM-03)`. Against old
   hosts the composer keeps the existing local in-memory queue with today's rendering and
   actions; nothing labels it durable. The outbox is written only in durable mode.
3. **Edit / reorder / delete / send-now with revision handling.** Edit = take (delete +
   image rehydration into the composer, draft recovery via `replaceUserInput` +
   `setSelectedAttachments`); reorder = full-id-list `agent.queue.reorder` from the row
   menu; delete = confirmed `agent.queue.delete`; send-now = take then the regular submit
   path, requeueing (at the end) if the submit fails. Every mutation sends the revision the
   device last saw; `queue_revision_conflict` surfaces as a visible localized conflict
   message plus an automatic queue refresh — never a silent overwrite. Tested in actions
   tests and e2e test 2.
4. **Retry exhaustion / uncertain delivery visible.** Daemon `failed`/`uncertain` rows show
   a status badge and Retry/Discard; retry is the only resend path (daemon contract from
   TM-02, UI honors it). Outbox entries exhausted after 8 failed flushes park visible with
   Retry/Discard instead of the source's silent drop. Tested in the outbox model tests and
   e2e drain assertions.
5. **Steer / Queue / Interrupt affordances.** Unchanged from custom: send-behavior setting
   (`steer` default), the running-state queue button, and the stop button. The queue path
   behind the Queue affordance now lands in the durable queue when the host supports it.
6. **Typed-send default comparison (product decision — unchanged, as instructed).**
   Source default and ours are identical: `sendBehavior: "steer"` with the same
   `"interrupt" | "steer" | "queue"` enum, same settings section, same labels
   (`sendAndSteer` / `sendAndInterrupt` / `queueMessage`) — verified identical at both
   `51fb7693d` and the newer source head `f0d5507d2`
   (`packages/app/src/hooks/use-settings/storage.ts`). There is no default to reconcile;
   the only behavioral difference after this port is what "queue" queues (durable daemon
   queue when gated, local otherwise). No product decision is required on the default; the
   open product question below is the outbox exhaustion UX (item 4 in update-loop
   candidates).

## The two-client daemon e2e (feasible — done)

Ran on the in-process fake-provider harness, no provider credentials, no auth gates:

- **Mirroring test:** two independent `DaemonClient`s against one daemon. Client B enqueues
  while the agent is parked on a fake permission request; client A receives the same queue
  via `agent.queue.update`. B edits in place (`agent.queue.update`), A enqueues a second
  item, B reorders, a fresh client reconnects and `agent.queue.list` returns the reordered,
  edited queue; B deletes the second item; the permission resolves, the turn ends, the
  drain delivers the surviving item, both live clients see the queue empty, and the
  canonical timeline contains exactly one `user_message` with the edited text.
- **Conflict test:** client A mutates at revision N; client B's write carrying revision N is
  rejected with `queue_revision_conflict` and the queue still shows A's edit.

Coverage note: capability-absent behavior is split across layers rather than forced into the
e2e — an old-client simulation would need capability overrides in the test client; parse
compat and event gating for old/new peers are already covered by TM-02's
`messages.agent-queue.test.ts` (9 tests, rerun green), and the composer's old-host path is
the pre-existing local queue behavior exercised by the existing actions/submit/state tests.

## tmad-main-latest (`929f1add3`, PR #36) — update-loop classification

PR #36 ("preserve queued messages until host acknowledgement") is a durability hardening of
the same client layer this port ships, written against the source's own 51fb7693d shape.

Already covered by this port, in a different or stronger form:

- No silent deletion at the retry cap — we go further and park the entry visible with
  explicit retry/discard (PR #36 keeps retrying behind a one-time attention message; both
  preserve the payload).
- Snapshot reconciliation with a revision guard; outbox entries re-sent verbatim (PR #36
  adds intent-carrying resends against a wire that gained intent — ours has that natively).
- A failed send keeps its durable entry and its visible row.
- No ghost rows after acknowledgement: our rows converge through snapshots (an ack applies a
  snapshot containing the id; later snapshots keep it because it is a daemon row).

Remaining update-loop candidates if #36 is later classified for adoption:

1. **"Waiting to sync" label + action gating** for rows the latest snapshot does not
   contain (PR #36 blocks edit/send-now on un-accepted rows; ours surfaces a daemon error
   instead if a device acts on an un-acked row mid-flight).
2. **Per-agent blocking flush** — PR #36 makes a failing enqueue block later items for that
   agent while other agents proceed; ours flushes oldest-first across the server and bumps
   failures individually.
3. **Await durable outbox persistence before clearing the composer draft** (and gating
   dispatch on it), plus their `index.test.ts` persistence tests. Our `outbox.add` is a
   synchronous store write; AsyncStorage persistence lands asynchronously, so a hard kill
   in that window can lose the entry.
4. **Exhaustion UX product decision:** PR #36's one-time attention message with indefinite
   auto-retry vs. our parked-failed-with-explicit-retry. The plan's queue contract
   ("Preserve the item after the source outbox's eight-attempt limit… explicit retry or
   discard") is what we implemented; adopting #36's shape would need that contract line
   revisited by a human.

## Known gaps / deferred

1. **In-place item edit has no composer affordance.** The client ships
   `updateQueuedAgentMessage` and the daemon supports it, but the UI's edit is
   take-into-composer (source parity, same UX as the local queue). The composer additions
   beyond source are menu reorder, delete, retry, discard. An inline edit field is new
   product surface, not ported.
2. **`steer_strict` intent is not admitted by this UI.** Admission sends `intent: "queue"`
   only; the outbox carries the intent so a future voice admission (TM-04) can reuse the
   path unchanged. `agent.queue.retry`/`send_now` on `steer_strict` items work from the
   client methods.
3. **Send-now uses take+submit, not `agent.queue.send_now`.** Deliberate: the daemon's
   send-now is a head-of-line attempt that no-ops against a busy agent (and burns an
   attempt), while take+submit delivers immediately through the user's send behavior
   (steer default) — matching the button's promise and the source's UX, and still yielding
   exactly one canonical row. The `sendQueuedAgentMessageNow` client method ships for wire
   parity and tests. Design call recorded here for review.
4. **Optimistic-row race inherited from the source:** between the optimistic add and
   `outbox.add` (the image-encoding await), a concurrent broadcast can briefly erase the
   row; the enqueue response's snapshot restores it. Window is small and self-healing.
5. **Host downgrade with pending outbox entries:** entries written against a capable host
   stay in storage if the host later loses the flag; they are not flushed and not shown as
   queued against a host that cannot honor them. Documented in `docs/queue-mirroring.md`;
   a purge/adopt policy would be new product surface.
6. **UI parity captures not taken.** The plan's UI-fidelity bar (matched source/port
   captures on desktop/compact/native) applies to the Stream port's rehearsal pattern; the
   queue track's source UI is byte-identical to ours at the row level and the additions
   (badges, menu) have no source counterpart to compare against. Browser/native screenshot
   evidence was not produced on this host; a human pass on the dev app is the natural next
   check.
