## Summary

Give fork code on `custom` a durable path onto all three fleet hosts by publishing a **versioned fork CLI/daemon artifact** through a fork release channel that mirrors `docs/release.md`, then repointing each host daemon launcher at it — the systemd unit on ceres, the LaunchAgent plist on saturn/neptune — leaving the stock Paseo.app in place as a client. Two sittings: ceres end-to-end spike first, then both Macs; a third sitting exists only as an obstacle-discipline escape hatch, never a lowered bar. Tier T3 (external-durable): published versioned artifacts plus a runbook section that outlive the session.

Chosen in the ADR below: **public npm under a personal scope** (pack-time rewrite in fork-local release prep, dist-tag `fork`) and version scheme **0.7.0-beta.2.fork.1** (prerelease identifiers appended to the upstream base).

Consensus headline (pass-1 blocker): **the repoint is an invariant, not an event.** setup-paseo.sh is idempotent and regenerates launchers from defaults on every routine re-run (password rotation, hostname change, PASEO_WEB_UI toggle). The dotfiles patch therefore makes the fork pin a guarded, re-derivable input on BOTH start and restart paths, and the runbook carries a standing pin rule; rollback is the deliberate act of omitting the pin, never an accident of forgetting it.

## Intent Diff

Today: fork code exists only in the worktree; every fleet daemon runs stock 0.7.0-beta.2 (ceres via mise npm tool + system unit; Macs via LaunchAgent running the brew-prefix symlink into Paseo.app). No publishable channel exists because @getpaseo/\* is not publishable by this fork.

After: a named fork version (0.7.0-beta.2.fork.1) of the CLI/daemon is published once and installed on all three hosts; each launcher references it by explicit version (ceres: PASEO_TOOL pin in the unit; Macs: absolute versioned path in plist ProgramArguments) and every later setup-paseo.sh run re-applies that pin or refuses loudly; interactive `paseo` on PATH stays stock (ceres: mise @latest wrapper; Macs: brew symlink lockstepped with the app); the stock app remains the GUI client of forked daemons; the fleet runbook owns upgrade, rollback, pin discipline, and verification for the channel; nothing in upstream-owned files changes (all fork tooling lives under fork/).

## Principles

1. **Humans restart daemons.** Every daemon stop/start/restart on 6767 is typed by a human at a terminal. Agents stage (install, edit files, publish prep) but never bounce a daemon — on ceres they physically cannot (NoNewPrivileges), on the Macs they must not.
2. **One PATH, one `paseo`.** Fork code enters a host only through a version-pinned absolute reference in a launcher, never through PATH. The two-binaries rule is amended to a PATH-level rule, not an existence rule.
3. **Smoke before repoint.** Nothing is repointed on a host until the exact published artifact has been installed in a scratch location and run as a daemon on a scratch port with a scratch home, and verified to report the fork version.
4. **Ride existing machinery — and keep it honest under re-runs.** The channel reuses docs/release.md two-step shape, the repo release gates, setup-paseo.sh generation, and mise/npm resolution. Because that machinery is idempotent and defaults to stock, the fork pin must survive every routine re-run, not just the initial repoint.
5. **The repoint is an invariant; rollback is deliberate.** Every launcher regeneration on a fork host re-applies the pin (PASEO_TOOL on ceres, PASEO_FORK_BIN on the Macs); the generator warns loudly and refuses the rewrite when it detects a fork-pointing launcher and no pin; returning to stock means explicitly omitting the pin — one documented command, never an accident.

## Decision Drivers (top 3)

1. **Verified host machinery must keep working.** ceres upgrades through `sudo -E PASEO_TOOL=... ./scripts/setup-paseo.sh` (mise npm tool by name@version, unit ExecStart = mise exec pin); Macs get their plist generated by the same script. The channel must ride these, not replace them — including their idempotent re-run behavior.
2. **Distribution cost is dominated by the @getpaseo/\* web.** Internal workspace deps pin exact @getpaseo/\* versions, and compiled code carries THREE quoted runtime name sites — require.resolve("@getpaseo/server") and the packageJson.name gate (packages/cli/src/commands/daemon/local-daemon.ts:187,199) plus SERVER_PACKAGE_NAME = "@getpaseo/server" (packages/server/src/server/daemon-version.ts:3). Any non-@getpaseo artifact home pays either a pack-time rename of names AND compiled specifiers, or a bespoke installer. The choice with the most testable failure gate wins.
3. **6767 is load-bearing.** Every running agent, including the planning session itself, lives behind these daemons. Every step needs a pre-repoint smoke, a single-listener check, a one-command rollback, and a pin that cannot be silently dropped by a routine maintenance re-run.

## Viable Options

### Decision 1 — Artifact home

**Option A (CHOSEN): public npm under a personal scope, pack-time rewrite.** Publish the 7 workspace packages in the CLI install closure (highlight, relay, protocol, client, plugin, server, cli) as @scope/paseo-\* with internal pins rewritten at pack time by a fork-local release script; publish with `--tag fork`; push branch + `fork/v<version>` tag and a GitHub Release on the fork repo for provenance.

- Pros: mise (`PASEO_TOOL=npm:@scope/paseo-cli@<ver>`) and plain `npm install --prefix` both work natively on every host; version resolution by name@version; dist-tags; npm view/audit; zero per-host credentials; artifacts immutable and public-durable (T3); setup-paseo.sh needs no functional change on ceres — only the unpin guard.
- Cons: needs an npm account + personal scope (assumption, see Risks); pack-time rewrite must also patch compiled dist specifiers (`"@getpaseo/` -> `"@scope/paseo-`) or runtime resolution breaks; every fork release rebuilds+republishes 7 packages; public artifacts (license-permitted: Apache-2.0 per root package.json and LICENSE; keep LICENSE/NOTICE intact).
- In-repo rename variant REJECTED: renaming names in-repo = permanent rebase pain on every upstream bump across 7 package.json files + all import specifiers; the fork survey shows renames get reverted (BAS-More -> @bas-more/\* -> reverted across four commits).
- Bundled single-artifact (esbuild-style) variant REJECTED: the daemon closure includes native modules (node-pty 1.2.0-beta.15, sherpa-onnx-node) and runtime dynamic resolution (require.resolve walks the server package root; the server itself depends on esbuild at runtime) — a single-file bundle is high-risk with no offsetting benefit over 7 plain tarballs.

**Option B: GitHub Packages (@camerontaylor scope on npm.pkg.github.com).** Same 7-package publish as A.

- Invalidated: GitHub Packages npm requires per-host auth (scoped .npmrc + token) even for reads. The fork repo is public (a fork of a public repo), so the packages would be public anyway — the auth burden buys zero privacy and adds a credential to maintain on three hosts plus the systemd/launchd install contexts and token rotation. Strictly worse than A.

**Option C: versioned tarballs on the fork GitHub Releases, names unchanged.** npm pack the 7 packages, attach to a Release; internal deps rewritten to release-asset tarball URLs.

- Pros: no registry, no account, no compiled-code changes (names unchanged so require.resolve("@getpaseo/server") works untouched).
- Cons/invalidation as plan of record: breaks name@version resolution — mise PASEO_TOOL and the ceres runbook flow cannot consume URL deps; needs a bespoke per-host installer script (the ad-hoc shape the pre-resolved mechanism decision excludes); no dist-tag floating resolution; npm URL-deps are a legacy path with rough edges. RETAINED AS DOCUMENTED FALLBACK if the npm-scope assumption fails (sitting 3 trigger).

### Decision 2 — Fork version naming vs upstream betas

**Candidate 1 (CHOSEN): prerelease identifiers appended to the upstream base — `0.7.0-beta.2.fork.1`.**

- Semver precedence: 0.7.0-beta.2 < 0.7.0-beta.2.fork.1 < 0.7.0-beta.3 (equal-prefix prerelease lists sort by length; numeric 2 < 3 bounds it above). The fork sits strictly between the beta it is based on and the next upstream beta — never older than the stock it replaces, never claiming to be the next beta.
- Encodes the base explicitly: `paseo --version` and server_info.version (resolved by walking package.json by SERVER_PACKAGE_NAME — packages/server/src/server/daemon-version.ts) both show the base and the fork build. Obvious in the stock app UI.
- Never collides with any upstream string while upstream ships betas: upstream prereleases are beta.N integers only (scripts/release-version-utils.mjs rejects any other prerelease shape), never dotted sub-identifiers.
- npm: valid prerelease; publish with `--tag fork` (never latest/beta). mise: no `+` characters, parses as a plain version.
- **Stable-base evolution, pre-committed (pass-1 F2):** when upstream promotes beta.2 to 0.7.0 stable, the scheme becomes `0.7.0-fork.1`, which is a prerelease of 0.7.0 and sorts BELOW the stock 0.7.0 it replaces (semver §11). No npm-hostable scheme fixes that against a future stable base, so the never-older property is explicitly transferred at promotion time to (a) the base-floor runbook rule — a fork host is only repointed when the fork base >= the installed stock client version — and (b) the protocol-compatibility contract — an older fork daemon must keep parsing the newer stock app in both directions, with features gating on server_info capability flags, never on version comparison (docs/protocol-compatibility.md). The ordering loss is accepted and documented, not discovered later.

**Candidate 2: build metadata — `0.7.0-beta.2+fork.1`.**

- Invalidated: semver ignores build metadata in precedence, so fork.1 and fork.2 of the same base compare EQUAL — npm dist-tag/highest-version resolution and lockfile selection become ambiguous between successive fork releases; `+` is also fragile in mise tool-version strings and gets truncated by naive version parsers. Fails the never-collide/obvious bar.

**Candidate 3: own prerelease line — `0.7.0-fork.1`.**

- Runner-up: valid, obvious, never collides. Rejected as the primary scheme: the upstream base is implicit (fork.2 does not say which beta it rides), and it sorts ABOVE every 0.7.0 beta including ones newer than its base — dishonest ordering as the codebase moves. It is PRE-COMMITTED as the stable-base continuation of candidate 1 (see above). Also the fallback if candidate 1 hits a tooling snag in sitting 1 (record the reason in ADR follow-ups).

Dist-tag policy: fork publishes only ever move the `fork` tag in the fork scope. Hosts pin exact versions in launchers; no floating installs of the daemon anywhere (mirrors the Mac cask install-only discipline). Note (pass-1 F4c): the first `--tag fork` publish leaves NO `latest` dist-tag on the fresh scope, so a bare `npm install @scope/paseo-cli` errors — that is correct for a pinned fleet; the runbook documents it so nobody fixes it by moving `latest`.

## ADR — Fork release channel: artifact home, version scheme, plugin posture

- **Decision:** Publish the fork CLI/daemon as 7 packages on public npm under a personal scope (@scope/paseo-{highlight,relay,protocol,client,plugin,server,cli}) via pack-time rewrite in fork-local release prep; dist-tag `fork`. Version scheme 0.7.0-beta.2.fork.1 (upstream base + .fork.N), with the stable-base continuation pre-committed as 0.7.0-fork.1 once upstream promotes the base to stable. Tag fork/v<ver> on origin; GitHub Release carries tarballs + notes. Hosts pin exact versions: ceres via PASEO_TOOL in setup-paseo.sh; Macs via versioned npm prefix + absolute path in plist ProgramArguments; the pin is a guarded invariant, not a one-time edit. The rename is npm-specifier-only by construction: wire-protocol field names (isPaseoOwnedWorktree and every other field) are untouched by design — field-level renames are where forks die (fork survey). Third-party plugins are declared OUT OF SCOPE for the fork channel.
- **Drivers:** the three Decision Drivers above.
- **Alternatives considered:** GitHub Packages (per-host read auth for no privacy gain); GitHub Releases tarballs with unchanged names (no compiled-code risk but breaks name@version resolution and the ceres mise flow, needs a bespoke installer) — retained as documented fallback; in-repo rename (rebase pain, historically reverted); single bundled artifact (native modules + runtime dynamic resolution make it high-risk); version schemes 0.7.0-beta.2+fork.1 (precedence ties) and a primary 0.7.0-fork.1 line (implicit base, dishonest ordering while the base is a beta); a tagged COMPAT alias restoring the original plugin SDK spellings in the staged rewrite — rejected: plugin-sdk-specifiers.ts dual-resolves @paseo/plugin* (legacy, COMPAT-tagged, removal 2026-11-19) and @getpaseo/plugin* (current), and a mechanical rewrite renames the current spelling leaving only the legacy one recognized; restoring the spellings would give recognition, but the SDK package exists under the fork only as @scope/paseo-plugin, so a plugin importing the original spelling still could not resolve it from the fork install — the alias would promise more than it delivers. Declaring plugins out of scope (fleet runs none today) is the honest posture; the alias is revisited only if that changes.
- **Why chosen:** preserves every verified host mechanism (mise name@version on ceres, npm install on Macs, plist/unit generation by setup-paseo.sh) AND their idempotent re-run behavior via the guarded pin; needs zero per-host credentials; yields immutable versioned public artifacts (the T3 bar); and its one real risk (rename rewrite misses) has a cheap, deterministic detection gate (pack-list grep + three-site inventory + scratch smoke) instead of a diffuse one (bespoke installers per host).
- **Consequences:** every fork release republishes 7 packages and rewrites compiled specifiers in the staged copy; the fork daemon can never use the built-in daemon self-update (its npm -g @getpaseo/cli inspect fails under mise/prefix installs — a safe error, and upgrades are runbook-owned anyway); the stock app displays a fork-suffixed daemon version, so the CLI/desktop lockstep rule gains a documented fork-channel amendment (daemon = app beta + .fork.N, drift tolerated by the protocol contract, features gate); an npm account/scope is now fleet infrastructure; the fresh scope carries no `latest` dist-tag by design (bare installs error — hosts pin exact); once the base is a stable 0.7.0, fork versions sort below that stable and the never-older property is carried by the base-floor runbook rule plus the protocol-compatibility contract instead of semver; third-party plugins are unsupported under the fork daemon until a follow-up decides otherwise.
- **Follow-ups:** confirm the npm scope name and record it in the runbook; after the first upstream beta bump, exercise the rebase -> fork-release -> per-host upgrade loop and time it; at the first stable-base promotion, exercise the 0.7.0-fork.1 naming and re-verify the base-floor + protocol-compatibility story end to end; revisit plugin support (tagged COMPAT alias PLUS a resolvable SDK, or a documented @getpaseo/plugin shim package) only if the fleet adopts plugins; revisit candidate 3 as primary only if a tool rejects dotted prerelease identifiers.

## Risks and mitigations

- npm scope does not exist / publishing publicly is refused -> assumption recorded; flip to Option C (documented fallback) in sitting 3; plan structure unchanged.
- Routine setup-paseo.sh re-run drops the pin (password rotation, hostname change, PASEO_WEB_UI toggle) -> the unpin guard refuses the launcher rewrite without the pin or the explicit override; restart paths exec the pinned binary; the runbook standing invariant; the pinned no-op re-run check in AC2.
- Stock CLI restart silently reverts a Mac daemon (restart respawns from the calling CLI require.resolve) -> PASEO_FORK_BIN on BOTH restart_macos_daemon branches; verification includes daemon version after any script-driven restart.
- node-pty/sherpa-onnx native gaps on darwin arm64/x64 -> proven in the per-Mac scratch smoke before any swap; Xcode CLT present or prebuilds ship; failure = sitting 3 trigger, host stays stock.
- mise rejects the dotted prerelease version string -> caught by the sitting 1 scratch `mise install`; fallback = candidate 3 as primary, recorded in ADR follow-ups.
- Fork repo workflows fire on push -> avoided by fork/-prefixed tags (triggers verified: v\* tags, main branch); branch pushes of custom are inert (branches: [main]).
- Stable-base promotion makes fork sort below stock stable -> pre-committed in the ADR; base-floor runbook rule + protocol-compatibility contract carry the never-older property; follow-up drill at first promotion.
- Plugin SDK specifier rename strands @getpaseo/plugin-importing plugins -> plugins declared out of scope for the fork channel, stated in the runbook; COMPAT-alias follow-up only if plugins are ever adopted.
- Fresh scope has no `latest` dist-tag -> documented in the runbook as intentional; nobody moves `latest` to fix a bare install that hosts are not supposed to do.
- Stock app beta auto-update advances the app past the fork base -> runbook base-floor rule: after any app update, check daemon floor (fork base >= app version) and rebase+release+repoint; protocol contract keeps old-app/new-daemon parsing safe in both directions in the meantime (docs/protocol-compatibility.md).
- Daemon self-update invoked against a fork daemon -> install-origin validation fails (not an npm -g @getpaseo/cli install) -> safe error, no action; noted in the runbook so nobody tries to fix it.
- Fresh scratch home downloads speech models -> mitigated for free by PASEO_LOCAL_SPEECH_AUTO_DOWNLOAD=0 / PASEO_DICTATION_ENABLED=0 / PASEO_VOICE_MODE_ENABLED=0 on the scratch daemon command (the repo own test-env knobs, packages/cli/tests/setup.ts:18-20).
- Two-binaries tension (deliberate) -> owned by Principle 2 + the amended runbook rule: interactive `paseo` stays stock (ceres: the 12_paseo.zsh mise wrapper pins stock @latest; Macs: brew symlink), fork binaries appear only as versioned absolute references in launchers.
