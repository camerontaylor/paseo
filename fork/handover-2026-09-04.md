### 2. Issue-and-return for the ownerless interrupt (plan §11, A6+C4; AC 17)

`GjcACPAgentSession.interrupt()` awaits `issueTerminalAbort`, which awaits the full
`_gjc/sdk/control` response (`gjc-acp-agent.ts:361` and `:329`, awaiting
`extMethod` at `:548`). The plan requires: install the stop, write the `turn.abort`
request, return once the write is dispatched. The response promise is tracked on the
stop and validated whenever it lands; a late rejection is logged and never
terminalizes.

Why it matters today: gjc's abort can legitimately take up to its own 10-second
budget, the manager's `interruptSession` wait (`agent-manager.ts:2931-2967`) is
shorter, `interruptReturned` goes false, and `cancelAgentRun` returns `refused`
(`agent-manager.ts:2865-2867`). A healthy slow abort gets reported as a failed Stop.

Shape of the fix: keep the synchronous prefix of `issueTerminalAbort` (identity
check, revision bump, idempotency key, `provider.gjc.abort_attempt` log), then issue
`extMethod` without awaiting and attach handlers that call the existing
`recordAbortResult` (`gjc-acp-agent.ts:574-593`) — it already does newest-wins,
validation, and release. Both interrupt branches (repeated stop and fresh install)
stop awaiting it.

Add GJC test 32: interrupt resolves before the control response resolves; the
response validates later; a late rejection never terminalizes. Expect existing tests
that resolve the control deferred after `await interrupt()` to need reordering — the
write is still issued synchronously, so `abortRequests` length assertions hold.

### 3. Terminal-reason precedence on ownerless release (plan §11, A4/C5; AC 6)

`maybeReleaseOwnerlessStop` emits `turn_canceled` unconditionally
(`gjc-acp-agent.ts:614-619`). The validated disposition must pick the reason:

- verdict `"safe"` (validated `stopped`) → `turn_canceled` — the abort genuinely
  stopped the turn, even if the eligible idle arrived first;
- verdict `"conditional"` (`no_active_turn` + `terminal_no_effect`) →
  `turn_completed` — nothing was left to stop, so the turn completed naturally and
  the post-stop idle is that completion edge.

Exactly one terminal either way — `terminalDelivered` (`acp-agent.ts:3604-3607`)
already guarantees once. Add GJC test 24 (both halves). This was iteration 3's C5,
filed against exactly this unconditional line.

### 5. Settle-as-failed on transport/process death (plan §2, A3; AC 15)

> **Superseded — the rationale below is wrong.** `connection.cancel()` is an SDK _notification_
> whose write errors are swallowed, so an undelivered cancel settles as **success**, not pending:
> the gate opens on proof it does not have. The forever-pending path is GJC's `extMethod`, whose
> pending responses are never rejected on stream end. See corrections 1 and 2 in
> [plans/plan-cancellation-boundary-fix-pass.md](plans/plan-cancellation-boundary-fix-pass.md).
> The remedy (settle as failed on death) still stands; its ordering and scope change.

No code path settles in-flight ledger writes when the process dies. The exit handler
(`acp-agent.ts:3125-3140`) synthesizes the foreground terminal — which records
terminal proof — but the in-flight `cancelAttempts` entry stays pending forever, so
`isCancelLedgerSatisfied` (`acp-agent.ts:2023-2033`) never opens and the staged
successor burns the full 10-second deadline before `expireStagedSuccessor` rejects.

Fix: on observed death, mark every unsettled attempt of the current stop
settled/failed (gate on `stopIdentityMatches` so a stop captured on an older
connection is untouched), then reject the staged successor immediately with a
death-specific reason instead of leaving it to the deadline. Route `close()`
(`acp-agent.ts:2806-2813`) through the same helper — it currently drops the record,
which matches in effect for waiters but not in letter, and there should be one death
path. Add generic test 21.
