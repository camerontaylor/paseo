# Fork differences against 0.13.2

Assessment on 2026-10-27. Keep the remaining behavior unless a row explicitly recommends retirement. Most permanent differences still solve problems absent from 0.13.2. Plugins can replace several feature implementations, but cannot repair the host's loader, built-in provider lifecycle, protocol projection, native selection, or Electron quit handling.

## Comparison boundary

- Target: upstream `v0.13.2`, `d2941157a`; previous base: `v0.13.0`, `d34d17a90`.
- Permanent source before this sync: `custom@7dd67b921`. The current checkout's `fix/unified-fork-build-version` has that same head; its name does not identify a separate implemented version change.
- The Neptune manifest also carries `origin/upgrade/basket-0.12.0@568972505`, `origin/upgrade/basket-0.13@6fe8977d9`, and `origin/fix/tree-kill-spare-detached@402d083f5`. These are assessed separately below. The second basket includes the first, so their feature counts must not be added together.
- The basket assessment reads its cumulative source delta against 0.13.0 and checks it against the changes in 0.13.1/2. It does not claim that the basket has been rebuilt or tested on 0.13.2. Unpublished TMAD candidate worktrees are outside the live manifest and this inventory.
- [The file inventory](audit-0.13.2-files.json) records the exact original comparison inputs and changed paths. Tests, translations and documentation travel with their owning behavior; they are not separate product features.

The seven commits from 0.13.0 to 0.13.2 contain release metadata and three fixes: sidebar hydration (`f9ac58b18`, #7896), Reanimated stale-view updates (`4cbbac563`, #7907), and animation/layout lifecycle cleanup (`3b67e20d8`, #7914). The last includes Worklets/Reanimated updates, bottom-sheet listener cleanup and Markdown settled-row measurement. They do not introduce a general replacement for our side conversations, queue, accounts, artifacts or custom provider cancellation contract.

Plugin judgments refer to the **stock 0.13.2 API**, not hypothetical new hooks. “Yes” permits a different plugin-owned surface. “Partial” means the workflow can move, but an existing built-in surface, provider operation or atomicity guarantee still needs core support. “No” means the present fix belongs in the host. These are source-based feasibility assessments, not completed plugin ports.

## Recommended cleanup and extraction order

1. **Retire stale carry labels and duplicate production hunks first:** #3545, #3950, snapshot-only #4101, #3369 hints, #7179 and #7169. Their old branches are already folded into serial baskets; do not delete a basket manifest line to remove one topic. Build a successor owner that preserves its other changes and regression coverage.
2. **Move self-contained features to plugins:** GJC provider, artifact index/feed, project PR browser, then Stream/companion feed. These have credible plugin-owned homes. Test against stock 0.13.2 as well as the fork; avoid accidentally depending on fork RPCs.
3. **Move configuration/tooling out of core:** worktree acceleration can be a project setup script; ZCode can reject unsupported prompts itself; release orchestration can live in an external repository. Migrate daemon appended policy to AGENTS/per-provider configuration before dropping exclusions.
4. **Keep host fixes:** SDK alias/type-declaration loading, Usage negotiation, closed-session fences, built-in ACP cancellation, native selection, timeline byte bounds, attention/notifications, queue admission/receipts and detached-tree termination. Plugins do not currently expose the required interception points.

Each extraction needs implementation and parity checks before it replaces a carry.
