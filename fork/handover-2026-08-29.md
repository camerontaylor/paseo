## Migrating to neptune

### What breaks

**Worktrees.** Worktrees store absolute paths, so moving or copying this directory
breaks every one of them. Paseo has since reaped four of the six that existed when this
was written — `hardcore-monkey`, `plan-gjc-acp-busy-turn`, `plan-fork-release-channel`
and `lavish-eagle`. Nothing was lost; every branch they held is pushed. The one that
still has work in it is `read/side-conversations-phase1-plan`, mapped in
[side-conversations-merge-blocker.md](side-conversations-merge-blocker.md). Live
registrations as of 2026-08-30:

| Worktree                               | Branch                   |
| -------------------------------------- | ------------------------ |
| `/home/ctaylor/repos/paseo`            | `custom` (this checkout) |
| `/home/ctaylor/.paseo-fork/build-tree` | `mine` (PR grab basket)  |

The Paseo-managed ones live outside this directory, under
`~/.paseo/worktrees/`. Their `.git` files point back into
`/home/ctaylor/repos/paseo/.git/worktrees/<name>`. Neptune is macOS, so the home
prefix is `/Users/ctaylor` and none of those paths resolve. Decide per worktree
whether it travels; `git worktree prune` after the move clears the dead registrations.

**Gitignored files that git will not carry.** Hand-copy these or recreate them:

- `.git/info/exclude` — contains `.omc/`. Not part of any commit, so re-add it by hand.
- `CLAUDE.local.md` is **not** one of these. Its content is tracked at
  `fork/claude-local.md`; the root file is a symlink to it, and the symlink is itself
  ignored. Recreate it with `ln -s fork/claude-local.md CLAUDE.local.md` — see
  `fork/README.md`.
- `.gjc/` and `.omc/` — local agent state.
- No `.dev/` exists here; the dev daemon has never run in this checkout.

**Do not copy `node_modules/`.** Neptune is macOS x64 and this tree is Linux x64;
electron, expo, and the `@gajae-code/natives`-style binaries are platform-specific.
Run `npm ci` on the other side.

**Regenerate, don't copy:** `packages/protocol/src/generated/validation/ws-outbound.aot.ts`
is zod-aot output (see `docs/protocol-validation.md`), plus the `tsconfig.tsbuildinfo`
files.

**macOS only: Spotlight will eat the install.** During neptune's `npm ci`, Spotlight
burned ~190% CPU (`mds_stores` 80%, `mds` 33%, four `mdworker_shared` at ~14%) against
npm's 35%, indexing every file of ~3,000 packages as npm wrote them. The machine was CPU
bound, not disk bound — swap was untouched. Spotlight has no glob or pattern rule, so the
only levers are a per-directory `.metadata_never_index` marker or excluding a parent
outright. Applied on both Macs on 2026-08-29: a sweep over every `node_modules` under
`~/repos` (3,963 on neptune, 869 on saturn), plus whole-tree markers on
`~/repos/worktrees` and `~/.paseo/worktrees` (the latter pre-created so Paseo's future
worktrees are born excluded). A _new_ clone under `~/repos` is not covered — re-run the
sweep, or accept a marker at `~/repos` itself, which also stops Spotlight finding source.

**Worktree convention across the fleet.** Verified 2026-08-29: no host sets `worktrees`
in `~/.paseo/config.json`, so all three default to `$PASEO_HOME/worktrees`, laid out
`<root>/<repo-hash>/<name>`. It _is_ configurable — `config.ts:487` reads
`worktrees.root`, tilde-expanded — but the decision was to leave it alone: Paseo owns its
hash-named tree, `~/repos/worktrees` stays for hand-made git worktrees, and the two
schemes never mix. Git itself has no worktree-base-dir setting; the path is per-command.

## Work in flight

### 1. The gjc ACP busy-turn bug (diagnosed, not fixed)

Paseo runs gjc as a generic ACP provider. A gjc session in ultragoal/goal mode keeps
running agent-initiated turns after its ACP turn ends. Paseo thinks the agent is idle,
so the next message goes out as a fresh `session/prompt` and gjc rejects it:

```
-32603  data={"code":"busy","details":"turn.prompt is unavailable while the agent is busy; use turn.steer explicitly."}
```

Observed live: agent `e9d0cdc1` (libris workspace) unusable ~1h, four occurrences in
`~/.paseo/daemon.log` between 13:25 and 13:45 on 2026-08-29.

The cause is missing turn **state**, not missing steering. Anchors, all verified
against `714524b76`:

- `agent-manager.ts:2437` `steerOrReplaceActiveTurn` → `:2444`
  `if (!expectedTurnId) return { status: "inactive" }`. With no known turn, the
  interrupt-and-replace fallback at `:2465-2478` never runs.
- Paseo already models agent-initiated turns: `agent-manager.ts:466-470` mints
  `autonomous-<uuid>`; `onStreamTurnStarted` at `:4225` calls `trackAutonomousRun` and
  `openActiveTurn`; `hasInFlightRun` at `:862` counts `activeTurnId`.
- Precedent to copy: `codex-app-server-agent.ts:5806` emits
  `{type:"turn_started", provider}` with no turnId on every native turn start.
- gjc already publishes the truth over ACP: in its source,
  `modes/acp/acp-agent.ts:2784` stamps `session_info_update` with
  `_meta {gjcPhase, gjcRunning}`, and the update pump has an ownerless branch. Paseo
  ignores `_meta` — zero repo-wide hits for `gjcPhase`.
- Paseo's hook point: `acp-agent.ts:2834 handleSessionInfoUpdate()` reads only `title`
  and `updatedAt` off exactly that update.
- Steering is reachable without leaving ACP: `@agentclientprotocol/sdk` `acp.d.ts:95`
  exposes `extMethod`; gjc routes `_gjc/sdk/control` at `sdk/acp/adapter.ts:506` into
  `control()` at `:372`; `turn.steer` is registered at
  `sdk/protocol/operation-registry.ts:76` and on no surface-policy denylist.
- No app change needed: `packages/app/src/composer/actions.ts:198` already sends
  `activeTurnBehavior: "steer"` whenever it has an `activeTurnId`.

Immediate workaround for a wedged agent: press Stop (ACP `session/cancel` →
`turn.abort`, admitted while busy), then send. Costs the running turn.

Two adjacent failures seen in the same logs, both separate issues: gjc's SDK prompt
deadline (`sdk.promptDeadlineMs`, default 30 min of zero attributable progress) firing
on a supervision loop, and a 289 KiB prompt exceeding the 256 KiB ACP transport limit.

### 4. Blocked: wedged provider refresh on ceres

Three `create_agent` calls and one `inspect_provider` all failed at exactly 120000ms
with `Timed out refreshing Gajae Code ... pending: initialize`, spawning no gjc
process at all.

gjc is not the problem: `gjc acp` answers `initialize` in 1.5s standalone and 1.5s
inside the new worktree with Paseo's exact env, and `gjc sdk session list` returns a
healthy broker index. Only one `gjc acp` process exists (serving the live libris
agent), so there is no orphan to kill. The likely trigger was two `create_agent` calls
fired in parallel, poisoning the in-flight refresh.

`paseo daemon reload` ("reload config.json without restarting the daemon") is the
non-destructive remedy and was not run — blocked by the permission classifier.
A daemon restart would also clear it but kills every running agent.
