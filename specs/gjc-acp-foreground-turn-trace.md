2. A stale GJC process, wrong daemon, version mismatch, or provider configuration causes old cancellation behavior.
3. The symptom is a UI, workspace aggregation, parent/child, or identity-correlation error rather than a backend failure.

## Hypothesis verdicts

### 1. Lifecycle-state divergence: supported

The live 2,004 ms boundary, manager log, adapter-local stack, and two separate foreground state holders converge. Paseo force-settled the manager run while its ACP adapter still owned the original prompt.

The immediate error is generated by Paseo's local ACP guard, not by a GJC busy response. GJC's delayed settlement exposes the integration defect.

### 2. Stale runtime or configuration: disconfirmed

- Paseo is the packaged `0.7.0-beta.2` daemon using `/Users/ctaylor/.paseo` on port 6767.
- The provider command is the absolute `/Users/ctaylor/.local/bin/gjc acp` and reports GJC `0.15.5`.
- The affected ACP frontend processes started after the installed package files. The five-second behavior lives in those frontends, not only in the older detached broker.
- No second Paseo daemon or alternate development home was active.
- GJC's setup check reports permission/abort-scope configuration drift, but neither setting changes the hard-coded settlement grace or explains the 2,004 ms boundary.

### 3. UI or identity error: disconfirmed for the matched incident

Paseo has legitimate parent/child, workspace aggregation, and provider-session identity distinctions. Here, the persisted snapshot and daemon stack identify the same Paseo agent, GJC provider session, request, and backend exception. The UI is reporting an authoritative failure.

## Adversarial qualifications

- The evidence proves that old-prompt settlement exceeded Paseo's two-second wait. It does not prove the old prompt resolved precisely at GJC's five-second fallback.
- The word `acknowledged` in Paseo's manager log overstates the ACP signal. The client knows that the cancel notification write completed, not that GJC processed it or that the prompt settled.
- This is a Paseo–GJC boundary defect, not conclusively a GJC-only defect. Paseo's manager assumes it may replace a run while the ACP adapter still enforces separate ownership.
- The earlier 3,640-second abandoned prompts are likely triggers and may indicate an additional GJC terminal/transport issue. They are not necessary to explain the foreground collision.
- No existing test covers the complete cancel-notification → two-second manager settlement → pending ACP prompt → immediate replacement sequence.

## Conclusion

The matched issue is a cancellation-settlement race in Paseo's generic ACP integration. Paseo force-clears manager state after two seconds without making the ACP adapter accept-ready. Current GJC can legitimately leave the original ACP prompt pending beyond that boundary, so Paseo's immediate replacement collides with its own adapter-local foreground guard.

The durable fix should enforce one ownership contract: a replacement must not start until the ACP adapter has terminalized or fenced the old prompt. Merely increasing Paseo's timeout above GJC's current five-second grace would reduce this instance but would keep correctness dependent on provider timing.

## Discriminating reproduction

Use a disposable ACP connection that accepts cancel immediately while resolving the original prompt after a controlled delay:

- Resolve at 1,500 ms: replacement should be admitted.
- Resolve at 5,000 ms: current Paseo should synthesize cancellation near 2,000 ms and then reproduce the local foreground-turn exception.

Capture cancel-notification write, manager synthetic cancellation, replacement admission, and old-prompt settlement timestamps. If the old prompt is already settled before replacement admission, investigate an independent stale adapter flag instead.
